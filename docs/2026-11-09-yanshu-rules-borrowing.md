# 从 yanshu 提炼的可借鉴开发规则（XimeYao 适配版）

> 日期：2026-11-09
> 来源：只读扫描 `D:\project\yanshu`（未写入、未运行其程序、未改动任何文件）。
> 引用纪律：本文一律用「文件 §章节」或符号定位，不用行号——理由见 `RULES.md` §3（行号在每次改动后都会过期）。
> 适用对象：XimeYao（Rust + TSF 五笔输入法，GPL-3.0-or-later）。

## 0. 结论先行

yanshu 值得抄的不是「更多规则」，而是三个机制：

1. **状态与历史分离**：`PROGRESS.md` 只保留 ≤150 行当前状态，历史验证流水外置到 `docs/verify/`。
2. **每条规则自带判据与出口**：写成「触发 → 动作 → 判据 → 无证据时怎么办」，并且尽量机检。
3. **把规则变成会话动作**：上班/下班打卡、质量门、双绿才允许 commit。

对 XimeYao 的优先级：**先做 1**（当前 PROGRESS 已 3378 行、DECISIONS 1323 行，是每轮会话最大的一笔上下文开销），**再做 3 的轻量版**（打卡 + 证据落盘），团队与视觉纪律按需最后上。

| `docs/verify/` | 验证证据档案 | 四列表 + 索引 |

让这套东西真正生效的是三个机制：

- **单源**：同一事实只在一个文件有正文，别处只留指针（`RULES.md` §2）。规则文件合计 ≤750 行，超限就拆写或删冗余，不许扩上限。
- **可判**：每条要么给命令/二值命题，要么给「标待确认」出口（`RULES.md` §1）。答不出「无证据时怎么办」的条目不许存在。
- **可执行**：`doccheck.mjs` 14 项结构检查 + `refcheck.mjs` 引用解析，双绿（退出码 0、失效引用 0）才允许本地 commit（`RULES.md` §5、§7）。

- `DECISIONS.md` 已 565KB / 197 条；靠「按 `## D-nnn` 标题直读」而不建索引，条目一多对检索能力要求高。

## 2. 可借鉴规则（A＝可直接抄，B＝改造后用）

### A1 状态文件 ≤150 行，历史外置

- 规则要点：`PROGRESS.md` 只写当前状态，区块固定为「接手指南 / 当前状态 / 进行中 / 下一步 / 验证记录 / 已完成 / 未决」。已完成只留一行摘要 + 指针；满 15 行就把最早条目整段迁 `docs/verify/completed-*.md`，原地不留指针行（`WORKFLOW.md` §6）。
- 为什么：yanshu 当初也把全部验证流水内嵌在 PROGRESS（164 行，占 40.9%），后按 D-060 整体外置——`docs/verify/README.md` 写明了这次迁移的理由：每个新会话都被要求整份读它，实际 99% 的时间用不到。
- XimeYao 现状（实测）：`PROGRESS.md` 3378 行 / 284KB，10 个二级标题、114 个三级标题，历史与状态混在一起；`## 下一步` 下面全是已勾选的 `[x]`，没有真正的「下一步」。
- 落地判据：新 `PROGRESS.md` ≤150 行；任何读者 30 秒内能答出「当前阶段 / 下一个功能点 / 阻断项」；历史条目只出现在 `docs/verify/` 且可回读。

### A2 决策编号化，append-only，必带「遗留」

- 规则要点：每条 `## D-nnn 标题`，字段固定「日期 / 状态 / 背景 / 决策 / 理由 / 影响与代价 / 遗留」，每条 ≤50 行；历史条目不溯改，新条目用新格式（`DECISIONS.md` D-001、`RULES.md` §8）。
- 为什么：日期标题无法被引用；有了 `D-nnn`，PROGRESS、验证档案、提交信息、代码注释才能指回同一个理由。yanshu 的 PROGRESS 明确写「需要哪条决策直接读 DECISIONS.md 的 `## D-nnn` 标题」。
- XimeYao 现状（实测）：`DECISIONS.md` 1323 行 / 117KB，全部是日期标题（如 `## 2026-10-27 托盘常驻 owner + F 键修复`），无编号、无状态字段；1323 行里只有 1 条带「遗留」小节，其余条目没有承接字段。
- 落地判据：新取舍必须有一条 `D-nnn`；答不出「当时为什么这么做」的改动视为未记录；「遗留：无」也必须写，防止理由烂尾。

### A3 验证证据四列 + 未验证直说

- 规则要点：端到端通过 = 真跑过且证据可回读，写入 `docs/verify/YYYY-MM-DD-<topic>.md`，固定四列：**平台（含版本）/ 命令或操作步骤 / 实际输出（退出码 + 关键片段）/ 是否覆盖各平台**；未验证就写「未验证」（`WORKFLOW.md` §4）。
- 为什么：yanshu 的判据很硬——「缺版本、缺步骤、只写『通过』而无输出 = 未验证」；对照算例、真开窗、窄窗尺寸都写进同一份记录，防止下轮用记忆补全。
- XimeYao 现状（实测）：没有 `docs/` 目录，验证结论都写在 PROGRESS 的叙述段落里，无法回读当时跑了什么；`cargo test --workspace` 最近记录 131 passed，但 CI 不跑它（见 §3）。
- 落地判据：新验证记录四列齐全；「已修复/已通过」必须能指到一条命令输出或一段实机步骤；跨宿主（记事本/浏览器/Office）与跨输入法状态（中/英、翻页、长词）没覆盖就写「未覆盖」。

### A4 规则条目模板与三档标签

- 模板（`RULES.md` §1）：

  ```
  - [G] 触发：<何时> → 动作：<做什么> → 判据：<命令/证据/二值命题> → 无证据时：<标待确认|停止|先取证>（出处：D-nnn / docs/verify 文件名）
  ```

- 标签：`[G]` 硬门禁（阈值、命令、枚举、退出码写死）；`[J]` 需专业裁量，只给原则+触发+审问句；`[F]` 事实，不设裁量，必须带「无证据时标待确认，不得补全」。
- 为什么：对 AI 代理来说，「要努力/要严谨」没有执行价值；「什么时候必须做什么、做完怎么算数、没证据怎么办」才有。
- 落地判据：单条 ≤200 字；解释或举证超 3 行就迁 `DECISIONS.md` 或验证档案；一条事实只出现一次正文。

### A5 单一 home + 零行号引用

- 规则要点：同一事实只允许一处正文，跨文件只准指针；引用只允许四类——全文直引、`文件 §章节`、`D-nnn`、代码/文档锚点（符号名、sha256 前 8 位）（`RULES.md` §3）。
- 禁止：`文件名:123`、`L12`、`第 N 行` 一类行号定位；无文件名的裸 `§n`。
- 为什么：行号在 AI 会话里 100% 会过期；`文件 §章节` 和符号名能解析、能 grep、能被下一个人复核。
- XimeYao 现状：AGENTS.md 已引用 `Cargo.toml`、脚本名，尚无行号债；趁早立规矩成本最低。
- 落地判据：文档与规则里 grep 不到 `\.md:\d`、`L\d{2,}`、`第\s*\d+\s*行`；引用了的 `§章节` 必须能解析到标题行。

### A6 问题处置三档

- ① 现在就修：阻断/高级别，或修它 ≤15 分钟且不扩范围（只动本卡文件、不引新接口）。
- ② 稍后修：只有说得出清理时机才允许登记——「在哪个功能点/哪个环节/谁的指令下清掉」；写不出时机的不许进表。
- ③ 判定不做：写明不做 + 理由 + 依据，append `DECISIONS.md`，不再挂成反复出现的未决行（`WORKFLOW.md` §5）。
- 判据：未决行缺时机、或同一事项跨轮反复出现 = 违规。
- 为什么：它直接对治「只登记不改」和「顺手重构」两个 AI 通病——前者制造垃圾清单，后者制造无法评审的混合 diff。

### A7 反 bug 漩涡（五条）

1. 修复前必答三句：复现步骤 / 根因假设 / 修好后应观察到什么。
2. 同一 bug 三次修不过 → 停手，先判是需求错、设计错还是实现错。
3. 同类缺陷合并修，不逐个打补丁。
4. 计算类用对照算例验证，界面类用复现步骤验证。
5. 修复必须带回归验证；无验证输出的「已修」＝未修（`TEAM.md` §4）。

XimeYao 适配：输入法缺陷几乎都带「宿主 × 输入法状态 × 键盘布局」三个维度，复现步骤必须写清宿主与版本（记事本 / Chrome / Word）、中英状态、是否翻页。

### A8 会话打卡

- 上班（`WORKFLOW.md` §1）：读 `AGENTS.md` + `WORKFLOW.md` + `PROGRESS.md` 全文 → `git status` / `git log` 一致性检查 → 扫未决表做三分类（阻断/相关/其余）→ 从「下一步」继续 → 一句话写明今天做什么、不做什么。
- 下班（`WORKFLOW.md` §2，第 8 步是硬门禁）：更新 PROGRESS（含销账：已解决的未决行**整行删掉**，不留删除线和「已关闭」占位）→ 追加 DECISIONS → 确认任务终态 → 双绿 → **本地 commit，不 push**。
- XimeYao 现状：AGENTS.md 已有简化版（读 PROGRESS/DECISIONS、build、下班更新、默认不 commit），缺三样：**销账规则**、**证据落盘**、**机检门禁**。

### B1 派单与团队纪律（用 AgentTeams 时）

- 候选≠必上：每轮按「真有几个独立视角」取 1–7 人；改一处文案 1 人就够（`TEAM.md` §0）。
- 作者不得复核自己的产出；单成员最多连做 3 张卡，第 4 张必须换人。
- 派单模板六项、≤500 字：目标（可验收）/ 范围与禁止项（inScope **目录带尾斜杠**，按前缀匹配）/ 输入（文件+章节，禁行号）/ 产出与落点 / 验收命令+期望输出 / 回报格式（≤300 字+文件路径）。
- 验收：成员回报「完成」不算数，队长自己跑命令或抽检；硬状态三件套 = `agent_teams_status` + inScope 文件 mtime + 相关进程存活，缺一按未知处理。
- 成本：每成员首次请求约 10 万 tokens（工具 schema 常驻）。XimeYao 多数任务是单点 bug，默认 1 人，跨层改动（TSF + server + UI）再上 2–3 人。

### B2 依赖与外部事实

- 先查再写：需要某通用能力且自写超过约 300 行，或涉格式/协议细节 → 先查 crates.io / 官方文档 / 本地源码（`CAPABILITIES.md` §7）。
- 依赖两条件、顺序不可颠倒：**许可允许 ∧ 本项目需要**；引入后五项落盘（workspace 统一版本、许可结论、「为何选 X 不选 Y」、PROGRESS 与能力文件各一行实测、重跑测试与边界检查）。
- 禁止臆造：库签名、CLI 参数、配置键、包名必须查证；无证据标「待确认」，不得用记忆补全（`CAPABILITIES.md` §4）。
- 事实优先级：产品事实 > 决策 > 一手实测/反编译 > 规范原文 > 对标实测 > 第三方文档 > 模型记忆（最低，不得单独作依据）。
- **XimeYao 要反向调整许可策略**：yanshu 是闭源商业软件，黑名单含 GPL/AGPL；XimeYao 本身是 GPL-3.0-or-later，GPL 系依赖可引入，但仍须记录来源与许可证，且「未声明许可」继续禁止。

### B3 上下文预算

- 工具输出 ≤5KB/回合，禁止目录全量 dump；大输出落盘只回「路径 + 结论」（`WORKFLOW.md` §7）。
- 不重复读未变文件；改文件优先用 edit；长日志用 tail。
- 真实 prompt（input+cacheRead）到 40M 必须落盘收尾，50M 强制收尾。
- 过程产物回收：一次性夹具、临时目录、探针输出，下班前删；下一轮没人会读的就删。

XimeYao 适配：MSI/MSIX 打包日志、`cargo build` 输出、Windows 事件日志都极长，统一落 `target/tmp/`，正文只留结论与退出码。

### B4 视觉与文案纪律（裁剪后）

yanshu 的 14 条里，可直接用于输入法的核心是：

- 颜色、字号、间距、圆角只取令牌；组件内禁裸值。
- 状态不能只靠颜色表达，必须有文字或图标；每屏至多一个强调色。
- 禁 emoji / Unicode 符号充当图标。
- 按钮写动作；错误写三要素「发生了什么 / 数据是否受影响 / 下一步」；禁英文堆栈与裸错误码。
- 空状态 = 一句说明 + 至少一个可点动作，只写「暂无数据」即违规。
- 动效只承载状态变化，120–200ms。
- 既有实现与纪律冲突时，不在功能点里顺手改，按三档处置。

为什么对输入法更要紧：yanshu 有一条实测教训（D-191）——断言 e2e 700+ 全绿仍漏 9 项界面缺陷（死 UI、NaN 印刷、布局错乱），断言抓不到「看得懂吗 / 点得动吗 / 错得体面吗」。候选栏的 6 态（空/单字/多字/长词/翻页/错误）、托盘图标状态、设置页空态，都属于这类。

### 5.1 PROGRESS.md 骨架

```markdown

> 本文件是当前状态的唯一正文；历史证据在 `docs/verify/`，取舍理由在 `DECISIONS.md`（按 `## D-nnn` 直读）。

## 接手指南（30 秒）
- 当前阶段：

## D-001 候选栏窗口尺寸按阴影半径外扩

**日期**：2026-11-09
**状态**：生效
**背景**：候选词少于 5 个时背景右侧被截断、无圆角。
**决策**：窗口尺寸改为 `(width + blur_radius * 2) * scale`。
**理由**：阴影需要 16*scale px 的绘制余量，固定 25px 预留不够。
**代价**：窗口比内容大一圈，命中区域随之扩大。
**遗留**：无
```

### 5.4 AGENTS.md 建议增补（5 条）

```markdown
## 状态与证据
- 状态：`PROGRESS.md` ≤150 行，只写当前状态与指针；历史验证记录写 `docs/verify/YYYY-MM-DD-<topic>.md`，
  四列固定（平台含版本 / 命令或步骤 / 实际输出 / 覆盖平台）。判据：只写「通过」而无输出 = 未验证。
- 决策：新的取舍写 `DECISIONS.md` 的 `## D-nnn`，字段固定（日期/状态/背景/决策/理由/代价/遗留），
  每条 ≤50 行；历史条目不溯改。判据：答不出「为什么」的改动 = 未记录。

## 规则写法
- 每条规则写成「触发 → 动作 → 判据 → 无证据时怎么办」；判据要能当场回答（命令/二值命题/可目视证据）。
  单条 ≤200 字，超出的解释迁 `DECISIONS.md` 或验证档案。
- 文档引用只用 `文件 §章节`、`D-nnn` 或符号名；禁行号（`文件:123`、`L12`、`第 N 行`）。

## 问题处置
- 发现本卡外的问题按三档：现在就修（≤15 分钟且不扩范围）/ 说得出清理时机才登记 / 判定不做写 DECISIONS。
- 同一 bug 三次修不过 → 停手先判需求/设计/实现哪层错；修复必须附回归验证。
```
